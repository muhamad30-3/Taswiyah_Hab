# إعداد التخزين المركزي

يستخدم التخزين المركزي PostgreSQL لتخزين جلسة التسوية، وبيانات مراحل المطابقة، ومشاريع الاستكمال كقيم JSONB مرتبطة بحساب الخادم. عند تفعيل هذا الوضع، لا يرجع التطبيق إلى التخزين المحلي إذا تعذر الاتصال؛ بل يعرض خطأ حتى لا يعطي انطباعاً بأن البيانات حُفظت.

## إعداد قاعدة البيانات

1. أنشئ PostgreSQL وقاعدة بيانات مخصصة للتطبيق لدى مزود الاستضافة.
2. اضبط متغيرات البيئة التالية **على خادم API فقط**:

| المتغير | الاستخدام |
| --- | --- |
| `DATABASE_URL` | عنوان اتصال PostgreSQL الخاص بالخادم |
| `CENTRAL_STORAGE_ENABLED` | القيمة `true` لتفعيل الدخول والتخزين المركزي |
| `APP_USERNAME` | اسم حساب التطبيق |
| `APP_PASSWORD` | كلمة مرور المسؤول الأولي، 6 محارف على الأقل؛ يُسمح بكلمة مرور من 6 أرقام |
| `APP_EMAIL` | بريد المسؤول الأولي (اختياري) |
| `APP_SESSION_SECRET` | سر عشوائي لا يقل عن 32 بايت لتوقيع جلسات الدخول |
| `APP_ORIGIN` | أصل الواجهة المسموح به، مثل `https://taswiyah.example.com` |
| `PORT` | منفذ خادم API |
| `API_TLS_KEY_PATH` و`API_TLS_CERT_PATH` | مسارا مفتاح TLS الخاص والشهادة؛ اضبطهما معاً فقط عند إنهاء HTTPS مباشرة في Node.js |

أنشئ قيمة سر الجلسة محلياً باستخدام Node.js، ولا تضعها في المستودع أو في كود الواجهة:

```powershell
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

3. مع ضبط `DATABASE_URL` في بيئة التنفيذ، أنشئ جداول الحسابات والتخزين والملفات:

```powershell
pnpm --dir lib/db run push
```

ثم فعّل RLS على جداول المخطط `public` لمنع الوصول المباشر عبر أدوار Supabase العامة:

```powershell
psql "$env:DATABASE_URL" -v ON_ERROR_STOP=1 -f lib/db/sql/enable-rls.sql
```

يمكن أيضاً تنفيذ محتوى `lib/db/sql/enable-rls.sql` من محرر SQL في Supabase. لا توجد سياسات قراءة أو كتابة عامة عمداً؛ عند تفعيل RLS من دون سياسات يكون الوصول مرفوضاً افتراضياً. التطبيق يستخدم جلسات موقعة خاصة به، وليست جلسات Supabase Auth، لذلك `auth.uid()` لا يطابق معرّفات `app_users`. يمر الوصول المصرح به من خلال خادم API فقط، الذي يتحقق من الجلسة ويقيّد بيانات المشاريع والملفات بمعرّف المالك. يجب أن يتصل الخادم بدور قاعدة بيانات يملك الجداول أو يتجاوز RLS؛ لا تضع بيانات الاتصال بهذا الدور في الواجهة.

لتحسين استعلامات قائمة المستخدمين والملفات، أنشئ الفهارس الإضافية بعد الجداول:

```powershell
psql "$env:DATABASE_URL" -v ON_ERROR_STOP=1 -f lib/db/sql/performance-indexes.sql
```

المفتاح الأساسي لـ`app_data (owner, key)` مفهرس مسبقاً، لذلك لا يضيف التطبيق فهرساً مكرراً له.

4. اجعل `VITE_CENTRAL_STORAGE=true` في بيئة بناء الواجهة، وأعد بناء الواجهة. في التطوير يمرّر Vite `/api` إلى خادم API؛ وفي الإنتاج يجب تقديم الواجهة وAPI تحت الأصل نفسه أو ضبط `APP_ORIGIN` وreverse proxy بعناية.
5. أنشئ في بناء النشر طبقة قاعدة البيانات قبل خادم API، مثلاً:

```powershell
pnpm --dir lib/db exec tsc -p tsconfig.json
```

للتطوير المحلي على Windows أو غيره، شغّل `pnpm dev` من جذر المشروع لتشغيل الواجهة والـAPI معاً. يستخدم `pnpm dev:web` لتشغيل الواجهة وحدها عند تشغيل API في عملية أخرى. يتصل Vite افتراضياً بـ `http://localhost:3000`؛ عدّل `API_SERVER_URL` فقط إذا كان خادم API يستمع على عنوان آخر.

## تشغيل ومراقبة الإنتاج

- اضبط `APP_ORIGIN` على أصل الواجهة الواحد فقط، مثل `https://taswiyah.example.com`، من دون مسار أو wildcard. يرفض الخادم أصلاً غير صالح، ولا يسمح بأصل HTTP عند `NODE_ENV=production`. لا تفعّل `TRUST_PROXY=true` إلا إذا كان الخادم خلف reverse proxy موثوق يضبط ترويسات forwarding.
- الخيار الموصى به للإنتاج هو إنهاء HTTPS عند reverse proxy أو منصة الاستضافة، ثم تمرير `/api` إلى خادم Node.js على شبكة داخلية. إذا أردت إنهاء HTTPS مباشرة في Node.js، وفّر شهادة TLS موثوقة وسلسلتها ومفتاحها الخاص على الخادم، واضبط `API_TLS_CERT_PATH` و`API_TLS_KEY_PATH` إلى مسارات الملفات؛ يجب ضبط الاثنين معاً، ولا تضع ملفات الشهادة أو المفتاح في Git أو مجلد الواجهة. سيستمع الخادم عبر HTTPS على `PORT`. لا تستخدم شهادة self-signed للزوار في الإنتاج.
- في التطوير، يوجّه Vite `/api` إلى `API_SERVER_URL`، والافتراضي `http://localhost:3000`. عند تشغيل API على HTTPS، اجعل `API_SERVER_URL` عنوان HTTPS الصحيح مثل `https://localhost:3000`؛ يتحقق Vite من صيغة العنوان قبل التشغيل. لا تعطّل التحقق من شهادة الخادم.
- على VPS Linux، ابنِ الخادم ثم شغّله باستخدام PM2: `pnpm --dir artifacts/api-server run build` ثم `pm2 start ecosystem.config.cjs --env production` و`pm2 save`. أعد تشغيل PM2 بعد النشر بـ `pm2 reload ecosystem.config.cjs --env production`. يحتفظ الإعداد بعامل واحد لأن محددات المحاولات والجلسات المؤقتة مخزنة في ذاكرة العملية.
- يسجل الخادم أخطاء المسارات عبر Pino ويحجب ترويسات `cookie` و`authorization`. افحص سجلات `pm2 logs taswiyah-api` ونقطة `/api/health`. يمكن إضافة Sentry أو مزود مماثل عند اختيار سياسة الاحتفاظ وموقع معالجة البيانات؛ لا ترسل بيانات التسويات أو المستندات إليه، وخزّن DSN في إعدادات الخادم فقط.
- فعّل النسخ الاحتياطي اليومي المشفر من لوحة مزود PostgreSQL، وحدد مدة الاحتفاظ والتنبيهات، ثم اختبر استعادة نسخة إلى قاعدة منفصلة دورياً. لا تحفظ ملفات النسخ في المستودع أو داخل مجلد الويب. إعداد النسخ الاحتياطي يعتمد على مزود قاعدة البيانات وخطة الاستضافة، ولا يمكن تفعيله من التطبيق وحده.

## الدخول والحماية

- يُنشأ حساب المسؤول من `APP_USERNAME` و`APP_PASSWORD` عند أول طلب دخول أو تسجيل. تُخزّن كلمة المرور كتجزئة scrypt، ولا يعاد استبدال كلمة مرور قاعدة البيانات بتغيير متغير البيئة بعد إنشاء الحساب.
- التسجيل العام وكلمات المرور الجديدة تتطلب 6 محارف على الأقل وبحد أقصى 256 محرفاً؛ يُسمح بكلمات المرور المكوّنة من أرقام فقط. تبقى كلمات مرور الحسابات الحالية صالحة للدخول من دون فرض إعادة تعيين؛ وتبدأ الحسابات الجديدة بحالة انتظار حتى يعتمدها المسؤول.
- يستطيع المستخدم المسجل تغيير كلمة مروره من صفحة الملف الشخصي بإدخال كلمة المرور الحالية والجديدة. يجب أن تتكون كلمة المرور الجديدة من 6 محارف على الأقل وبحد أقصى 256 محرفاً، ويمكن أن تكون أرقاماً فقط؛ وتُخزّن كتجزئة scrypt.
- الدخول بعد الاعتماد يستخدم اسم المستخدم وكلمة المرور فقط. يعرض النظام صفحة إدارة المستخدمين للمسؤول وحده، كما يتحقق الخادم من صلاحية المسؤول على كل طلب إداري.
- تبقى كلمة المرور وسر الجلسة على الخادم. لا تضعهما في متغير يبدأ بـ `VITE_`.
- يرسل الخادم جلسة موقعة داخل cookie من نوع `HttpOnly` و`SameSite=Strict`، ويُضاف `Secure` في الإنتاج.
- يحد الخادم محاولات الدخول، ويربط بيانات الجلسات والمشاريع باسم الحساب المسجل. تُرحّل بيانات الحساب القديم إلى اسم المسؤول الموحّد عند الحاجة.
- لكل حساب مكتبة ملفات خاصة به. تُحفظ الملفات في PostgreSQL مع اسمها ونوعها وحجمها وتاريخ رفعها، ولا يمكن للمستخدم تنزيل أو حذف ملف يخص حساباً آخر. الحد الأقصى للملف الواحد 25 ميغابايت.
- تحتفظ جلسة المتصفح بملفات منصة A مؤقتاً لتبقى متاحة عند الانتقال بين A وB وC؛ لا تُضاف ملفات المصدر إلى «ملفاتي» إلا عند حفظ المشروع. يؤدي مسح الجلسة إلى حذف النسخ المؤقتة، ولا يمس الملفات والمشاريع المحفوظة.
- الأنواع المدعومة: Excel وCSV، PDF، Word وOpenDocument، PowerPoint، النصوص، والصور الشائعة. تسمح واجهة الملفات بتنزيل نسخة من الملف لإعادة إدخالها في أدوات العمل.
- تُرحّل بيانات المتصفح القديمة إلى حساب المسؤول فقط، ولا تُنسخ تلقائياً إلى حسابات المستخدمين الجدد.

البيانات المخزنة تشمل المعلومات الخام المستعملة لاستعادة العمل، لا المطابقات الظاهرة فقط. لا تُحذف صفوف المصدر الصفرية أو غير القابلة للمطابقة عند الاسترجاع؛ وتعرض الواجهة عدد صفوف الفواتير والحوالات الخام بعد الاستيراد. قد لا تدخل بعض الصفوف المطابقة التلقائية إذا كان مبلغها صفرياً أو غير صالح، لكنها تبقى محفوظة في المصدر.
تُضغط قيم التخزين المركزي الكبيرة بـgzip قبل حفظها في JSONB، ويعيدها API مضغوطة لعملاء HTTP الداعمين مع الإبقاء على شكل الاستجابة الحالي. تتحول القيم القديمة تلقائياً عند أول قراءة ناجحة، ما يقلل حجم البيانات بين قاعدة البيانات والخادم والواجهة في القراءات التالية.

## ملاحظات التشغيل

- لا تضع بيانات اتصال أو كلمات مرور في المستودع. يلزم تهيئة PostgreSQL ومتغيرات الخادم قبل تفعيل هذا الوضع.
- أنشئ نسخة احتياطية دورية من قاعدة البيانات؛ الملفات الثنائية وبيانات المشاريع محفوظة فيها.
- خذ نسخاً احتياطية دورية من PostgreSQL. تصدير Excel يبقى خياراً منفصلاً للاستعادة اليدوية.

## نشر الخادم على Railway مع الواجهة على Vercel

يجب نشر خادم API منفصلاً عن ملفات الواجهة الثابتة. يعالج ملف `railway.json` في جذر المستودع بناء خادم API وتشغيله وفحص صحته.

1. أنشئ مشروعاً وخدمة Railway من هذا المستودع، وأضف PostgreSQL إلى المشروع. اترك جذر الخدمة في جذر المستودع كي يجد Railway ملف `railway.json` وملف قفل pnpm.
2. أضف متغيرات الخادم المذكورة أعلاه في إعدادات خدمة API. استخدم عنوان PostgreSQL الداخلي الذي توفره Railway في `DATABASE_URL`، واضبط `CENTRAL_STORAGE_ENABLED=true`، وولّد `APP_SESSION_SECRET` محلياً. عيّن `APP_ORIGIN` إلى أصل الواجهة المنشورة على Vercel. لا تضف أسرار الخادم إلى متغيرات Vercel التي تبدأ بـ`VITE_`.
3. بعد جاهزية قاعدة البيانات، أنشئ جداول التطبيق وفق خطوات إعداد قاعدة البيانات أعلاه. لا تفتح صلاحيات قاعدة البيانات للعامة.
4. فعّل النطاق العام لخدمة API على Railway، ثم تحقق من أن `https://<api-domain>/api/healthz` يعيد `{"status":"ok"}`.
5. وجّه طلبات `/api/*` في إعدادات Vercel إلى `https://<api-domain>/api/*` باستخدام rewrite، بحيث تبقى طلبات المتصفح على نطاق Vercel نفسه وتعمل ملفات الجلسات. يجب أن يطابق `APP_ORIGIN` النطاق الذي يرسل المستخدم منه الطلبات.
6. اضبط `VITE_CENTRAL_STORAGE=true` في بيئة بناء Vercel وأعد النشر. لا تفعّلها قبل أن يكون API وقاعدة البيانات جاهزين ومتاحين عبر rewrite؛ وإلا ستظهر أخطاء عند تسجيل الدخول والتخزين.
